# 1. KRITISK BUGG — SÖKSTRÄNGEN FÅR INTE BLI PERSONENS STAD

## Problem

Merinfo-sökningen byggs nu korrekt exempelvis som:

```text
168 50 Bromma
```

Men i `scrapa_alla.py` sparas fortfarande sökvariabeln `stad` i råpersonen:

```python
person_dict = {
    ...
    "stad": stad,
}
```

I detta scenario innehåller `stad`:

```text
168 50 Bromma
```

Det är en **söksträng**, inte personens faktiska postort.

Sedan prioriterar `_person_to_result()` i nuläget ungefär:

```python
city = override_city or p.get("stad", "") or _extrahera_ort_fran_adress(adress)
```

Det gör att en korrekt person med adress:

```text
Zornvägen 38, 168 50 Bromma
```

kan få:

```text
city = "168 50 Bromma"
```

istället för:

```text
city = "Bromma"
```

Geo-validatorn jämför därefter:

```text
168 50 bromma
```

mot:

```text
bromma
```

och personen kan felaktigt rejectas.

Detta är en blockerande bug.

---

# 2. FIXA SOURCE OF TRUTH FÖR CITY

Den faktiska scrapade adressen ska vara **source of truth** för postort.

Söksträngen får aldrig användas som verifierad city.

Implementera principen:

```python
actual_city = _extrahera_ort_fran_adress(adress)
```

och använd i första hand:

```python
city = actual_city
```

Fallback får endast användas om faktisk ort verkligen inte kan extraheras.

Exempel på rimlig ordning:

```python
city = (
    _extrahera_ort_fran_adress(adress)
    or verified_city_from_provider
    or ""
)
```

Använd INTE:

```text
search query
```

som verifierad city.

---

# 3. FIXA `scrapa_alla.py`

I råposten ska söksträngen inte längre sparas som:

```python
"stad": stad
```

om `stad` innehåller:

```text
168 50 Bromma
```

Antingen:

* lämna `stad` tom och låt normalizer extrahera faktisk ort ur adressen
* eller spara faktiskt extraherad postort

Om söksträngen fortfarande behövs för debugging ska den sparas separat, exempelvis:

```python
"search_location": "168 50 Bromma"
```

men aldrig i personens verifierade `city`/`stad`.

# 5. BALANCED — TAPPA INTE RESTEN AV EN SIDA

Det finns fortfarande en viktig v0.3-bugg i Balanced mode.

## Problem

Exempel:

```text
Target = 10

Area A quota = 5
Area B quota = 5
```

Area A har på sida 1:

```text
10 kvalificerade personer
```

Nuvarande motor kan göra:

```text
Person 1
Person 2
Person 3
Person 4
Person 5
```

och stoppa direkt när lokal quota 5 nås.

Sedan sätts nästa sida till:

```text
page = 2
```

Problemet är att:

```text
person 6–10 på sida 1
```

aldrig processas.

Om Area B bara kan ge:

```text
2 personer
```

och systemet senare återbesöker A går det direkt till sida 2.

De återstående personerna på sida 1 är då permanent tappade.

---

# 6. BALANCED — RÄTT BETEENDE

Skilj på:

```text
GLOBAL TARGET
```

och:

```text
LOCAL AREA QUOTA
```

## Global target

Får stoppa exakt inne i personloopen.

Exempel:

```text
Target = 500
Qualified = 500
```

→ stoppa omedelbart.

Vi vill aldrig få 501.

---

## Lokal Balanced-quota

Får INTE orsaka att oprocessade personer på aktuell sida försvinner.

En enkel och robust lösning är:

> Processa klart aktuell sida när endast lokal quota nås.

Efter sidan kan området få status:

```text
quota_reached
```

Exempel:

```text
Quota = 100
```

men sidan gör att resultatet blir:

```text
107
```

Det är acceptabelt.

Balanced ska vara:

> så jämnt som praktiskt möjligt

inte exakt på individnivå om det leder till bortkastade kandidater.

---

# 7. ALTERNATIVT RESUME-OFFSET

Om implementationen istället väljer att stoppa mitt på sida måste den spara exakt offset inom sidan.

Exempel:

```text
page = 1
offset = 5
```

så nästa pass kan fortsätta med person 6 på samma sida.

Men detta är mer komplicerat.

För nuvarande LARP föredras den enklare lösningen:

```text
local quota → stoppa efter aktuell sida
global target → stoppa exakt direkt
```

# 9. `quota_reached` SKA FORTSATT VARA SEPARAT FRÅN `exhausted`

Behåll separationen:

```text
quota_reached
```

betyder:

> området har uppnått sin nuvarande fairness-kvot men kan ha fler personer.

```text
exhausted
```

betyder:

> datakällan har faktiskt inga fler användbara kandidater.

Om ett område når sin quota mitt på eller efter en sida ska det inte felaktigt markeras som exhausted.

# 13. VALIDERA POSTNUMMER PÅ BACKEND

UI:t har postnummerinput, men backend ska inte acceptera godtyckliga värden.

Efter normalisering:

```text
168 50
```

→

```text
16850
```

ska värdet matcha:

```regex
^\d{5}$
```

Godkända:

```text
16850
16764
11435
```

Reject:

```text
1685
ABC
123456
16A50
```

Backend måste validera detta även om frontend redan gör det.
