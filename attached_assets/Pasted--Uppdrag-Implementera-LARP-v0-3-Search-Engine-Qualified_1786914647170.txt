# MÅL

Efter denna fas ska användaren kunna säga:

> Jag vill ha 500 personer med telefonnummer från dessa fem postnummer.

LARP får då kontrollera exempelvis 900, 1 500 eller fler råa personer om det behövs.

Systemet får **inte** stoppa bara för att 500 personer har lästs.

Det ska stoppa när:

```text
qualified_count == target_count
```

1. **Jämn fördelning**
2. **Nå totalmålet**
3. **Töm varje område**

# DEL 1 — FIXA AGE EXTRACTION

## Problem

Frontend kan redan visa `age`, men ålder extraheras inte stabilt från Merinfo-resultaten.

Personkorten kan innehålla information som gör det möjligt att bestämma ålder, exempelvis:

```text
19981023-****
```

eller annan födelsedatumsrepresentation samt ibland explicit text som:

```text
27 år
```

Vi vill visa **ålder**, inte lagra maskerat personnummer.

## Implementera

Skapa en tydlig central funktion, exempelvis:

```python
_extract_age(...)
```

eller motsvarande namn som passar befintlig kodstandard.

Prioritet:

### 1. Explicit ålder

Om texten innehåller:

```text
27 år
```

använd `27`.

### 2. Födelsedatum

Om personkortet innehåller födelsedatum/personnummer där födelsedelen kan utläsas, exempelvis:

```text
19981023-****
19981023
1998-10-23
```

beräkna korrekt ålder från **år + månad + dag**.

Använd aktuell datumjämförelse så att personen inte får +1 år innan födelsedagen passerat.

Exempel:

```python
age = today.year - birth_date.year

if (today.month, today.day) < (birth_date.month, birth_date.day):
    age -= 1
```

### 3. Saknad data

Om ålder inte kan fastställas:

```python
age = None
```

eller befintlig motsvarande representation.

Visa då `—` eller tomt enligt nuvarande UI-konvention.

## Viktigt

Lagra INTE det maskerade personnumret som permanent persondata.

Vi behöver endast:

```text
age
```

Födelsedatan får användas temporärt för beräkningen.

## Säkerhet

Regexen ska inte råka tolka:

* postnummer
* telefonnummer
* andra numeriska strängar

som födelsedatum.

Validera rimliga datum.

# DEL 2 — SEPARERA `scanned_count` OCH `qualified_count`

Detta är den viktigaste förändringen.

Idag blandas i praktiken:

```text
hur många råa personer vi har gått igenom
```

med:

```text
hur många personer som uppfyller användarens krav
```

Det ska separeras fullständigt.

## Definitioner

### scanned_count

Antalet råa personposter som motorn faktiskt har undersökt.

Exempel:

```text
scanned_count = 842
```

### qualified_count

Antalet **unika** personer som efter normalisering, deduplicering och filter uppfyller kraven.

Exempel:

```text
qualified_count = 500
```

## Ordningen måste vara

```text
raw result
↓
normalize
↓
deduplicate
↓
apply filters
↓
qualified?
↓
qualified_count += 1
```

En dubblett får alltså INTE öka `qualified_count`.

# DEL 3 — `target_count` SKA BETYDA GODKÄNDA RESULTAT

## Exempel

Användaren väljer:

```text
Target: 500

Filters:
✓ Must have phone
```

Systemet hittar:

```text
Scanned:   100
Qualified: 58
```

Det ska fortsätta.

Sedan:

```text
Scanned:   500
Qualified: 314
```

Det ska fortfarande fortsätta.

Sedan:

```text
Scanned:   817
Qualified: 500
```

NU ska systemet stoppa.

## Ta bort gammalt tänk

Använd inte längre en fast gissning som:

```python
raw_limit = target * 10
```

som själva stoppregeln.

En estimator får finnas för intern planering om det hjälper, men den får **inte definiera när jobbet är klart**.

Det riktiga stoppkriteriet ska vara:

```python
qualified_unique >= target_count
```

för lägen där ett totalmål används.

# DEL 4 — HARD SCAN BUDGET

Vi behöver samtidigt förhindra oändliga jobb.

Inför därför en separat:

```text
hard_scan_budget
```

Exempel:

```text
Target: 500
Hard scan budget: 10 000
```

## Princip

Jobbet får fortsätta tills någon av följande blir sann:

### Success

```text
qualified_count >= target_count
```

### Exhausted

Alla valda områden/källsidor är uttömda.

### Budget reached

```text
scanned_count >= hard_scan_budget
```

### Fatal error

Jobbet kan inte fortsätta.

## Default

Sätt ett rimligt defaultvärde.

Förslagsvis kan det beräknas från target men ska ha både min- och maxgräns.

Exempel:

```python
hard_scan_budget = max(target_count * 20, 2000)
```

med en absolut övre gräns enligt vad som är rimligt för nuvarande LARP.

Det exakta valet får anpassas efter befintlig implementation.

## UI

Det behöver inte vara ett stort avancerat fält.

Visa exempelvis:

```text
Safety scan limit
10 000
```

under Advanced settings, eller håll det internt i första versionen om det passar nuvarande UI bättre.

Men backend ska alltid ha gränsen.

# MODE A — JÄMN FÖRDELNING

UI-namn:

> **Jämnt mellan områden**

## Exempel

```text
Target: 500

Postnummer:
A
B
C
D
E
```

Initial quota:

```text
A 100
B 100
C 100
D 100
E 100
```

## Soft quotas

Kvoterna ska vara mjuka, inte hårda.

Om:

```text
A → 100
B → 72 och sedan uttömd
C → 100
D → 100
E → 100
```

saknas:

```text
28
```

Dessa ska fördelas mellan områden som fortfarande kan ge fler kvalificerade resultat.

Exempel slut:

```text
A 107
B 72
C 107
D 107
E 107

TOTAL = 500
```

Exakt fördelning får skilja med maximalt ungefär 1 mellan tillgängliga områden där det är praktiskt möjligt.

## Viktigt

Ett område som är uttömt får inte blockera hela jobbet.

Redistribuera underskottet automatiskt.

## Stop

Stoppa när:

```text
global qualified_count == target_count
```

eller alla områden är uttömda/budgeten nådd.

# MODE C — TÖM VARJE OMRÅDE

UI-namn:

> **Töm varje område**

Detta läge fungerar annorlunda.

Här finns inget globalt target som stoppkriterium.

Varje valt postnummer ska köras så långt som befintlig datakälla medger.

Exempel:

```text
13237 → 438
13246 → 271
13337 → 516

TOTAL → 1 225
```

## Stop per område

Ett område är klart när exempelvis:

* inga fler resultatsidor finns
* nästa sida ger 0 nya personer
* endast redan sedda resultat återkommer
* källan signalerar slut
* per-area scan budget nås
* fatal error uppstår

## Max per område

Om nuvarande UI behöver ett säkerhetstak kan vi ha:

```text
Max scan per postal code
```

eller använda hard scan-budget per område.

Men grundprincipen är:

> hämta så mycket som möjligt från varje valt postnummer.

# DEL 16 — DYNAMISK REDISTRIBUTION

Balanced mode behöver en liten scheduler/allocator.

Implementera så enkelt och robust som möjligt.

Princip:

```python
remaining_target = target_count - qualified_count
active_areas = areas that are not exhausted
```

När ett område inte kan fylla sin quota:

1. markera området `exhausted`
2. beräkna hur mycket som saknas
3. fördela detta på återstående aktiva områden
4. fortsätt

Vi behöver inte optimera perfekt matematisk fairness.

Kravet är:

> så jämnt som praktiskt möjligt utan att ett svagt område hindrar totalmålet.
